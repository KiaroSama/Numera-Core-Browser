# Chromium compiler continuation on standard runners

Windows and Linux cold developer builds ran through the measured 330-minute budget. Counting native Siso finish entries from both downloaded and digest-verified logs shows 27,197 C/C++ actions on Linux and 18,726 on Windows. Those labels account for 82.05% and 78.55% of entries in the observed portions of the two builds. This count measures actions. Actual cacheability, phase duration, total graph size and the remaining link work require direct measurement. [Action counts with run and log provenance](../evidence/cold-compile-action-profile.json)

The first probe acquired the pinned Chromium 157 source on two fresh standard GitHub-hosted jobs per selected OS. It generated the upstream GN graph with `use_siso=false` and `cc_wrapper="sccache"` in the initial probe mode. Both jobs verify the official Ninja and sccache release hashes. The seed requests the real `base/logging.cc` object through Ninja and saves a bounded cache archive scoped to its run and attempt. The resume job verifies the archive and manifest digests, exact runner/toolchain/command context and every member before reading it. It requires all compiler requests to hit the cache and the object to match the seed bytes. A controlled source change then requires a cache miss and different object bytes. [Pinned Chromium compiler wrapper](https://chromium.googlesource.com/chromium/src/+/4b3d0dabb8250b6f152d2d85d79e7706e309d087/build/toolchain/cc_wrapper.gni)

The archive is limited to 32 MiB per target and uses an exact Actions cache key. Diagnostic artifacts retain reports and logs. The experiment leaves GitHub's storage settings and the baseline cold recipe intact. Cache capacity for the full set of local outputs, time to replay generated actions, complete provenance, and the final link and renderer remain separate gates. [GitHub Actions storage and cache allowances](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

The first Linux seed finished all 649 Ninja steps for the requested object. sccache recorded 437 compile requests, zero writes and zero hits. It declined 369 requests with `-fmodules` and 68 with unknown `-Xclang` options. The seed therefore failed its cache-write gate and GitHub skipped the resume job. [Verified Linux probe result](../evidence/chromium-cache-probe-44836679704.json)

The Linux follow-up changes only the probe configuration. It uses hash-pinned ccache 4.14.3 with Clang modules off, Chromium's compiler analysis options retained, content-based compiler checking and preprocessed input keys. The proof is tied to the exact `logging.o` invocation in the ccache log so a cached prerequisite cannot satisfy it. The standalone native C++ fixture verified cold write, archive restore, exact-object hit and source mutation before the hosted follow-up. [Chromium's ccache guidance](https://chromium.googlesource.com/chromium/src/+/4b3d0dabb8250b6f152d2d85d79e7706e309d087/docs/linux/build_instructions.md#ccache)

The first Windows seed likewise compiled the object at Ninja step 625 of 625. sccache recorded 422 requests and zero writes. Of these, 421 used `-fmodules-cache-path` and one used `-x`. The follow-up using ccache 4.14.3 compiled the object in 622 steps and reported 421 unsupported-option requests, with zero cache writes. The retained log gives the aggregate statistic. Separately, ccache's source rejects clang-cl `/clang:` options, which the pinned Chromium graph uses for its compiler settings. The Windows sccache 0.19.0 probe keeps Chromium's `/clang:` arguments and turns off Clang modules in the probe graph. Ninja builds the object's prerequisites with a separate local cache. It reached 373 of 621 prerequisite actions before the 600-second limit. The isolated `logging.obj` request did not run. The retry allows 24 minutes for prerequisites, increases their disposable cache to 128 MiB and retains their statistics. The isolated probe archive still has a 32 MiB limit. Its seed and resume require exactly one target request, a write on a cold miss, a hit with the same bytes on the fresh runner and a miss with different bytes after changing the source. The staged Windows controller uses the same pinned wrapper and checks that imported cache members survive before it saves the next checkpoint. Native dispatch depends on the isolated replay result. [Prerequisite timing](../evidence/chromium-cache-probe-44845071989.json) · [sccache clang-cl options](https://github.com/mozilla/sccache/blob/v0.19.0/src/compiler/msvc.rs)

The corrected Windows seed completed all 621 Ninja prerequisites. Their separate sccache server recorded 402 writes and 18 local hits across 420 requests. The target server recorded a single request, one miss and one write for `logging.obj` with zero unsupported options or cache write errors. The 215,040-byte seed checkpoint was saved for a fresh Windows job. [Verified Windows seed](../evidence/chromium-cache-seed-44848971290.json)

The fresh Windows job rebuilt the graph and all prerequisites, then returned one verified sccache hit for the byte-identical `logging.obj`. Changing `base/logging.cc` produced one compiler cache miss, a new write and a different object hash. Both jobs reported the same runner image, compiler, GN arguments, source lock and SDK versions. This establishes reuse and invalidation for one isolated Windows object. The Windows full-graph workflow shares the staged concurrency group with Linux to bound repository cache usage. [Verified Windows replay](../evidence/chromium-cache-resume-44848971290.json)

The full-graph workflow uses at most four standard jobs on one target at a time. Each gets 275 minutes of local compilation after pinned graph preparation. It fingerprints the complete Ninja command stream, compiler, cache tool, GN settings, source lock, workspace and runner image. A timed segment can pass a digest-verified checkpoint only if it added local compiler outputs and did not evict entries. It checks the repository's current cache headroom before upload and never changes the quota. A native build that finishes runs the existing controlled renderer fixture and the verified Linux SUID helper where applicable. Source and renderer evidence remain separate from native automation, packaging, signing and production release approval.

The first ccache Linux seed wrote 436 real Chromium compiler results. Its archive was 19,056,640 bytes. The fresh resume job rebuilt the pinned graph but received runner image `20261116.376.1` instead of the seed's `20261116.133.1`. The verified reports agree on every other recorded input, including the exact compiler executable and requested compile command. The initial guard stopped before importing cached results. A second cold seed on `20261116.376.1` produced the same `logging.o` SHA-256 and again wrote 436 results. The Linux workflows record both image labels and allow only that metadata field to differ, with the exact verified preprocessed-only ccache configuration, run, compiler and command context required. Each new compilation is preprocessed before ccache looks up its result. The single-object resume additionally requires byte equality and a verified source-change miss. The second Linux seed's fresh resume job restored the checkpoint on runner image `20261116.376.1`, matching its seed image. All 436 cacheable compilations recorded preprocessed hits with zero misses, including the exact `logging.o` invocation. The object's SHA-256 matched the seed. Changing `base/logging.cc` produced one miss and a different object hash. The separate staged workflow entered native compilation for the full Linux graph at its frozen commit. The first full Linux segment stopped at its 275-minute compile budget with 29,769 of 56,773 observed actions. ccache recorded 24,601 outputs and zero evictions. The stage saved a 1,022,955,520-byte checkpoint with a verified configuration and member inventory. GitHub records a compressed size of 979,503,568 bytes under the exact run, attempt and stage key. The second job uses that checkpoint and reacquires the pinned source on a fresh host. Source linking and the native renderer will be measured in a completed segment. [Verified full-graph checkpoint](../evidence/chromium-staged-44846110371-segment-1.json) · [Live staged run](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/44846110371)

Once the staged build has linked both binaries, it starts the owned ChromeDriver on an automatically assigned loopback port, creates a W3C session using the exact built Chromium, and checks the renderer marker in the local fixture. The response-size and redirect regression runs before the first source segment. A separate locked suite then uses Selenium 4.53.0 over WebDriver, Puppeteer 25.18.1 over CDP and Playwright 1.65.1 via `connectOverCDP` with the same owned pair. Each client must navigate to the local fixture, verify the DOM marker and capture a PNG. The stage reports these results separately. This covers headless smoke tests. Native Playwright transport, headed sessions and the advanced operation matrix require their own evidence. [Pinned ChromeDriver server behavior](https://chromium.googlesource.com/chromium/src/+/4b3d0dabb8250b6f152d2d85d79e7706e309d087/chrome/test/chromedriver/server/chromedriver_server.cc) · [Playwright CDP attach](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp) · [Puppeteer connect](https://pptr.dev/api/puppeteer.connectoptions) · [Selenium Chrome options](https://www.selenium.dev/selenium/docs/api/javascript/module-selenium-webdriver_chrome-Options.html)

Subsequent staged runs also use the pinned GN `runtime_deps` inventory to copy the linked runtime into a scratch path with spaces and Persian characters. The fixture verifies the copied file hashes, temporarily moves the original build output and runs renderer and WebDriver checks with a separate profile. Windows uses the final top-level executable produced by the import-reorder action. The workflow retains a dependency and digest inventory. The Windows and Linux installer, corresponding source publication and publisher trust are separate release gates.
