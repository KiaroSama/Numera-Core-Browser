# Paths and packaging status

The requested default Windows project location is `G:\Program Files\Portable\Scripts\Numera-Core-Browser`, and the requested installed-program location is `G:\Program Files\Numera Core Browser`. These are user preferences, not assumptions about another machine or GitHub runner. There is no installer yet and no global PATH or PowerShell execution-policy mutation is performed.

Choose a private writable data root that already exists and a separate package store. On Linux the data root requires owner-only access. On Windows choose a local directory with ACLs restricted to the account that will run Core. Core confines profile and cache directories to the data root and rejects links and reparse-point traversal. Pure planning leaves paths untouched. The desktop launcher creates per-profile directories during authorized launch.

To retain data before changing an engine, stop the session and run `numera-core profiles snapshot DATA_ROOT SOURCE DESTINATION` with absolute paths beneath the same root. The destination must be new with an existing private parent. Core takes an exclusive native-profile lease and copies regular data to the new directory. The package binding is written after all files have been copied. A failed copy is left for inspection and cannot launch without a valid binding. An existing profile remains pinned to its original exact package. Data-format migration to a different build requires separate evidence.

Keep engine source workspaces outside the portable/runtime directory. Chromium source builds require paths without spaces; `numera-build-chromium --source-root` therefore requires an explicit absolute scratch source root. It never silently moves the user's project. GitHub jobs use their own runner scratch storage and do not assume a `G:` drive.

Engine manifest paths follow portable component rules. Inspection rejects Windows device aliases, invalid filename characters and trailing spaces or periods, including on Linux. Regression fixtures cover Persian filenames and Windows device names with extensions. [Windows filename rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)

Windows and Linux x86-64 are the distribution targets. The CLI builds independently and has no display, engine-download, Node or Python runtime requirement. The Linux x86-64 development Chromium archive passed native rendering, window, automation, ownership and relocation tests. Fresh Ubuntu 22.04 and 24.04 runners verified the published archive and opened a native window. Ubuntu 22.04 used its default sandbox with no administrator setup. The 24.04 runner's sandbox policy required the archive's verified `chrome_sandbox` helper, installed separately in job scratch. The installer, repair, removal and automatic update suites remain open. [Linux archive and attestation evidence](evidence/development-chromium-44983567389.json) · [Ubuntu 22.04 evidence](evidence/linux-retained-browser-45002016269.json) · [Ubuntu 24.04 evidence](evidence/linux-retained-browser-45000980622.json)

For an operator-installed signed Linux package on a host that requires the setuid sandbox, have the system administrator install the verified package's `chrome_sandbox` as a root-owned file with mode `4755` in a root-protected directory. Set `NUMERA_CHROMIUM_SANDBOX_HELPER` to that absolute path before starting the launcher or `numera-core serve`. Core checks the file against the exact selected package and rejects links or writable parent directories. Leave the variable unset on hosts where the default Chromium sandbox works. [Chromium sandbox setup](https://chromium.googlesource.com/chromium/src/+/6dc9bc3bdaea5c35ed6d41fceab2f7a3a2227c4f/docs/linux/suid_sandbox_development.md)
