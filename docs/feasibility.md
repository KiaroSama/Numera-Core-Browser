# Source-build feasibility — optimized build timed out; development build pending

The initial GitHub integration denied both repository-creation routes: GraphQL `createRepository` and REST `POST /user/repos` returned `Resource not accessible by integration` (REST HTTP 403). The user subsequently created the exact public repository and its prepared source history was published. No existing repository was renamed or overwritten.

The first public hosted spike is [run 42871431763](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/42871431763), against source commit `8c0bcf819c0fcded67e5b7a20d69c7fd68902419`. All four jobs retained real measurement artifacts and correctly failed the owned-engine gate. They did not build a browser. Exact runner image versions, tool paths, bytes, phases and times are retained in `docs/evidence/hosted-feasibility-42871431763`.

During this initial spike, source acquisition remained incomplete on Windows and Intel macOS. The scratch-file counts include partial source/build-tool acquisition files and are not the size of a complete engine checkout. The five-minute budget is a bounded probe limit, not GitHub's six-hour limit: these observations do **not** establish that a full build either can or cannot fit an allowed six-hour job.

Official GitHub documentation retrieved on 2026-11-10 lists 14 GB SSD for standard public runners and a 6-hour job limit. Current Chromium Windows prerequisites require at least 100 GB free NTFS space; current source paths must avoid spaces. These are a documented concern, not proof of the actual disk available on an unmeasured runner.

The initial feasibility workflow uses only standard `ubuntu-24.04`, `windows-2025-vs2026`, `macos-15` ARM64 and `macos-15-intel` jobs. It measures actual image/tools/disk before/after task-owned scratch preparation. It does not delete installed runner SDKs or unrelated system data. It initially uses a conservative 100 GB source-build safety budget based on the documented Windows minimum; per-platform minimums and toolchains still require validation.

If that budget is available, the bounded native recipe acquires pinned depot_tools and Chromium plus full source dependencies, checks the pinned revision and patch hashes, generates a reduced-symbol release build, and attempts the `chrome` target at parallelism 2. No browser objects, stock binaries, CEF packages, hidden remote execution or warm caches are used. A five-minute spike budget or 20 GB free-disk guard stops the owned source-tool process tree and preserves the exact attempted stage. Null measurements remain unmeasured. A successful compilation alone still cannot pass native acceptance/package/release gates.

The source recipe is a candidate, with PowerShell parsing checked separately from execution. Native SDK availability, GN arguments, sandbox behavior, final link/package size and reproducibility require actual hosted execution. No split-DAG or incremental cache approach has been proven. No paid/self-hosted fallback is authorized.

The separate `chromium-source.yml` workflow permits up to 330 minutes for cold source/dependency acquisition, Chrome/ChromeDriver compilation and controlled JavaScript/DOM/screenshot fixtures. The whole job is bounded to 350 minutes, below the hosted six-hour limit. Build-only `psutil` samples process-tree RSS and volume free space; evidence and the running job's check output are updated every 30 seconds. It does not create a separate check on another workflow's suite or set the Actions job's conclusion. Earlier small evidence artifacts expired after one day; current evidence retention is seven days. Browser objects and binaries are not cached or published.

The first full-budget [Windows run 42876581655](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/42876581655), at `a4b43089f43b333570376788853aef501340e4ec`, completed the pinned source checkout, dependencies and branding patch. Commit `e186d7cb92efbc43fb643e2c89c4b15fc5578831` explicitly runs the pinned CIPD/Windows bootstrap, probes its Python launcher and verifies the depot revision stayed pinned. [A fresh cold run](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/42881287336) was dispatched with the full 330-minute budget. The earlier failure is a recipe defect, not evidence of resource exhaustion. Compilation, final linking, artifact size, engine working set, native fixtures and warm behavior remain unmeasured until a subsequent run reaches them. Engine acceptance stays BLOCKED. Native Rust control-plane success is kept separate.

The last sampled phase still said patch application, but the retained native log and phase events prove GN generation was the actual failure. Commit `54eaa944150aea3d47b78b9d0b1d5c58b60de5fc` writes standard `args.gn` instead of sending nested string literals through a batch command line, and the monitor now reads the final phase after fast failures.

[The report](evidence/cold-source-42886710076.json) retains the measured stage and resources. This is a missing prerequisite, not an engine compile or resource-limit result.

The verified preparation recipe pins the official Microsoft SDK 10.0.28000.2957 installer (SHA-256 in `upstream/windows-sdk/lock.json`), checks its trusted Microsoft Authenticode publisher, installs only on the disposable authorized hosted machine, and verifies required headers/libraries/tools. [SDK-only run 42891690639](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/42891690639) passed in 231.187 seconds, with installer exit 0 and debugging tools 10.0.28000.2957. [Full cold run 42893263429](https://github.com/KiaroSama/Numera-Core-Browser/actions/runs/42893263429), at commit `79e9452268010f6aa28acd78e31e8045307c72ac`, includes SDK preparation, complete source acquisition, compilation/linking of Chrome and ChromeDriver, and controlled DOM/JavaScript/screenshot fixtures within the 330-minute budget. Local compiler concurrency is the requested ceiling (up to four), available CPUs and a conservative three GiB of initially available memory per compiler; requested/effective counts and memory are recorded. This gives the free runner's available capacity a measured attempt rather than assuming two workers are the infrastructure maximum. The heuristic is not proof of a universal engine memory minimum. Only evidence artifacts are retained; no stock engine, object cache, paid runner, remote compilation or hidden weakening is used.

The optimized fourth attempt actually exhausted its 330-minute budget at `compile-link`: the retained final check reports 19,801 seconds, 196.16 GB free and 7.23 GB peak sampled process-tree RSS. [Recovered evidence](evidence/cold-source-42893263429-summary.json) explicitly distinguishes rounded check values from the expired raw report. The public job log proves the timeout; the native compiler log/action count was only in the expired artifact and is unavailable. This is a failed bounded recipe, not proof that every configuration or all six hosted hours are insufficient. No renderer fixture ran.

The next candidate selects upstream's development configuration (`is_debug=true`, component build and zero symbol levels), retaining the sandbox, security boundaries and local-only compilation. This tests whether removing compiler optimization work lets the cold build fit; speed is not assumed. Native action counters, when present, are read from a bounded binary log tail and published live alongside effective compiler parallelism. Missing counters remain unmeasured. Attempted gates become `RUNNING`/`BLOCKED` instead of incorrectly remaining `NOT_RUN`; a passed source gate stays separate from fixture failure. Current reviewed source pins are Windows/macOS 157.0.8103.79 and Linux 157.0.8103.78. The branding patch passed exact-source checks; DEPS changes are recorded in [the research refresh](research/2026-11-13.md). A debug result cannot establish optimized release performance or release readiness.
