# ADR 003 — observe candidates before trusted activation

Feed observation and explicit offline TUF package administration are implemented. Publisher key provisioning and a signed production release remain separate acceptance work.

The 6-hour watcher reads official Chromium per-platform stable rollouts, Mozilla version metadata, WebKit revisions and official automation-client releases. It keeps one review-only candidate branch/PR and never changes approved source locks or merges/releases automatically. Puppeteer's client releases are distinguished from its separate browser-download package. New observations are not signed or trusted update metadata.

The first hosted run observed feeds and pushed the candidate branch, then GitHub rejected PR creation: `GitHub Actions is not permitted to create or approve pull requests`. The authorized user connection created draft PR #3; after the checkout/idempotency fix, a subsequent hosted watcher run passed and updated that same PR. The user then explicitly requested merging all existing side branches, including #3. This does not enable automatic merging of future candidates.

[The retained report](../evidence/permission-check-42890624858.json) records all cleanup outcomes. This tests new PR creation rather than a no-op or updating an existing PR. The integration itself still cannot administer repository settings. The watcher creates draft PRs and never approves reviews or merges. Under the user's branch-merge instruction, #4 was manually reviewed and merged after confirming its deferred WebKit revision exists; it changes observation metadata only. Candidate engines remain unapproved, source locks stay unchanged, and future watcher PRs are not merged automatically.

The store uses `tough` 0.24.0 to verify timestamp, snapshot and targets metadata against an independently provided trusted root. It persists accepted metadata floors and verifies root rotation before accepting a candidate. Keep the initial root and publisher signing keys under the operator's control. CI build attestations are separate from this root and do not authorize installation.

Publish a reviewed Chromium release archive whose regular files have paths under `runtime/`, including the actual license notices named by its manifest. Prepare the signed targets entry with `numera-core engines target ARCHIVE MANIFEST.json`. In the TUF repository use `numera-chromium-x86_64-unknown-linux-gnu.tar.gz` or `numera-chromium-x86_64-pc-windows-msvc.tar.gz` as the target name. Include the returned length, SHA-256, engine manifest and runtime inventory digest in publisher-signed targets metadata. Export the metadata and targets to `REPOSITORY/metadata/` and `REPOSITORY/targets/` using the usual TUF layout. [TUF specification](https://theupdateframework.github.io/specification/latest/) · [Official publisher tooling](https://github.com/awslabs/tough/tree/tough-v0.24.0/tuftool)

Use `numera-core updates check STORE TRUSTED_ROOT REPOSITORY` to verify metadata, `updates stage STORE TRUSTED_ROOT REPOSITORY` to verify and unpack the selected archive, and `updates activate STORE SHA256` to select it for eligible new profiles. `engines install STORE TRUSTED_ROOT REPOSITORY` stages and activates under the same store lock. `updates rollback STORE` restores the previous eligible default. An attached session holds a shared kernel lease on its exact package. Installed versions are retained for existing profiles and recovery. Browser profile data remains bound to its original digest, so a store rollback does not migrate or downgrade the original database. [Profile snapshots](../portability.md)
